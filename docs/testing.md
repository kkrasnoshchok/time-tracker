# Тестирование

Как проверяется качество проекта и что нужно проверить руками. Обновляется вместе с кодом.

## Автоматические проверки

| Что | Команда | Что считается успехом |
|---|---|---|
| Все тесты логики | `swift test --package-path Packages/TimeTrackerCore` | все тесты зелёные |
| Один набор | `swift test --package-path Packages/TimeTrackerCore --filter PaletteParserTests` | |
| Покрытие | `bash scripts/coverage.sh` (порог по умолчанию 90%, `bash scripts/coverage.sh 95`) | каждая папка модуля не ниже порога, код возврата 0 |
| Мутационное тестирование | `bash scripts/mutation.sh [файл-отчёта]` | см. раздел «Мутационное тестирование» |
| Линтер | `swiftlint` | 0 нарушений |
| Сборка приложения | `xcodegen generate && xcodebuild -scheme TimeTracker -destination 'platform=macOS' build \| xcbeautify` | `BUILD SUCCEEDED` |

Вся логика (Domain, Store, Palette, Journal, Export) лежит в пакете `TimeTrackerCore`, поэтому тесты запускаются без UI и выполняются за доли секунды.

## Что считается хорошим тестом

- Проверяет наблюдаемое поведение (результат, состояние хранилища), а не внутреннюю реализацию.
- Сначала виден красным (падает по понятной причине), потом зелёным.
- Детерминирован: время идёт из `TestTimeProvider`, хранилище в памяти, без `sleep`.
- Покрывает границы: пустой ввод, стыкующиеся записи, смена суток, переход на летнее время, юникод и эмодзи, CRLF в тексте.
- Ловит поломку: после ключевых изменений делаем ручную мутацию (ломаем строку кода и смотрим, что тест краснеет). Если не краснеет, добавляем тест.

## Мутационное тестирование

Инструмент: [Muter](https://github.com/muter-mutation-testing/muter) 16 (`brew install muter-mutation-testing/formulae/muter`, собирается из исходников около 3 минут).

Ограничения:
- **Muter 16 портит файлы с не-ASCII текстом** (смещения считаются в байтах): на `DurationFormat.swift` и `StoreError+Message.swift` он генерирует невалидный Swift, базовый прогон падает. Скрипт `scripts/mutation.sh` эти файлы пропускает. Они покрыты ручными мутациями (см. ниже).
- Muter копирует пакет в `Packages/TimeTrackerCore_mutated`; перед запуском скрипт удаляет `.build`, иначе базовый прогон в копии падает.
- Операторы Muter: замена операторов сравнения, смена логических связок, обмен веток тернарного оператора и удаление побочных эффектов. Это не все возможные поломки.

### Результат прогона (2026-10-18)

`scripts/mutation.sh` мутирует только файлы, которые Muter 16 не портит: `TimeSpan`, `PaletteParser`, `PaletteViewModel`, `TagInput`, `DayGrouping`, `EntryFilter`, `CSVExporter`. Пропущены: `DurationFormat`, `StoreError+Message` (кириллица), `TimeStore`, `TimeStore+Entries`, `JournalViewModel` (типизированный `throws(E) -> T`), `SQLiteExporter` (многострочная строка). Эти файлы покрыты ручными мутациями.

- Мутантов: 38, убито 33 (86% по отчёту Muter). Пять «выживших» разобраны вручную:

| Мутант | Вердикт |
|---|---|
| `DayGrouping.swift:32` (`>` на `>=`) | эквивалентный: добавляется ноль секунд |
| `PaletteParser.swift:9` (`count > 1` на `!= 1`) | эквивалентный: токен с `#` всегда длиной не меньше 1 |
| `EntryFilter.swift:28` | при ручной подстановке тест `filterByTag` падает; Muter не применяет мутации внутри замыканий надёжно |
| `PaletteViewModel.swift:193` (два мутанта) | при ручной подстановке тест `suggestionsComeFromRecentTitles` падает; та же причина |

- С поправкой на эквивалентные и ложные «выжившие»: все 36 неэквивалентных мутантов убиты.
- Ручная мутация вскрыла ещё один пробел, которого Muter не показал (многословный ввод с неизвестной категорией предлагал категории); добавлен тест `partialCategoryFollowedByMoreWordsOnlyOffersToCreate`.

Вывод: на этих файлах тесты ловят поломки; доверие к Muter ограничено его багами, поэтому ручные мутации остаются обязательным дополнением.


### Эквивалентные мутанты

Мутант, который не меняет поведения, не говорит о дыре в тестах:
- `PaletteParser.swift`: `token.count > 1` и `token.count != 1` равны, потому что токен с префиксом `#` всегда имеет длину не меньше 1.
- `JournalViewModel.exportRows`: сортировка по `start` была лишней (хранилище уже отдаёт записи по возрастанию начала), её удалили.

### Ручные мутации

В ходе работы вручную ломались и ловились тестами: остановка таймера без защиты от обратного хода часов; остановка предыдущей записи «сейчас» вместо нового начала; пропущенная проверка «старт раньше текущего таймера»; касание записей как пересечение; граница дня как `+86400` секунд (вскрыло пробел, добавлен тест на переход на летнее время); формульный префикс в CSV; удвоение кавычек; квотирование перевода строки (вскрыло настоящую ошибку с CRLF); сортировка тегов; пересоздание SQLite-файла; обновление подсказок после отправки; знак сдвига `-20m`; молчаливое создание категории; подтверждение пересечения; сброс подсказки при вводе; ложный `cancelPrompt`; форматирование времени (padding, порог часов, отрицательные значения); дедупликация тегов; порядок категорий.

## Ручная проверка (UI и хоткей)

Эти вещи нельзя проверить автоматически без прав Accessibility и Screen Recording. Агент, писавший код, их **не проверял**: он убедился только, что приложение собирается, запускается и не падает. Пройдите чек-лист и отметьте результат.

При первом запуске macOS может попросить права (например, на мониторинг ввода). Хоткей на базе `RegisterEventHotKey` обычно прав Accessibility не требует.

## Проверка внутри процесса (без прав Accessibility)

Права на скриншоты и управление интерфейсом нужны только для действий **извне** приложения. Но окно можно проверять изнутри: временный код в самом приложении создаёт настоящее окно палитры, шлёт ему события `NSEvent.keyEvent` через `window.sendEvent` (Return, Tab, Esc) и пишет состояние в лог. Так нашёлся баг двойного Enter (см. ниже), и так подтверждены Tab, Esc и создание категории. Этот стенд в репозиторий не вошёл; его можно вернуть, когда понадобится проверить ещё что-то в окне.

Что нельзя проверить даже так: сам глобальный хоткей, вид окна и работу с чужими приложениями.

### Баг двойного Enter (исправлен 2026-10-19)

- Симптом: на неизвестной категории первый Enter показывал вопрос, второй Enter ничего не делал.
- Причина: при Enter `TextField` записывает текст обратно в `viewModel.input` (то же значение) прямо перед `onSubmit`; `didSet` считал это правкой и стирал вопрос, поэтому каждый Enter был «первым».
- Исправление: `didSet` игнорирует запись неизменённого значения; добавлен `PaletteViewModel.reset()` при показе окна. Тесты: `writingTheSameInputBackKeepsThePrompt`, `resetClearsInputPromptAndItems`.
- Урок: юнит-тесты логики не видели этот баг, потому что не имитировали поведение настоящего поля ввода.

## Известные ограничения проверок
- Скриншоты и управление интерфейсом из сессии агента недоступны, поэтому раздел «Ручная проверка» остаётся за вами.
- Мутационное тестирование не охватывает файлы с кириллицей (см. выше).
