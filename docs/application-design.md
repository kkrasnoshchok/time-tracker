# Application Design

Личный трекер времени для macOS. Дата дизайна: 2026-10-10. Статус: черновик, ждёт ревью.

## 1. Цель и границы

**Цель.** Быстро и без усилий фиксировать, сколько и на что уходит времени в течение дня. Накопленные данные потом используются для дашбордов и аналитики, чтобы улучшать привычки.

**Главное требование.** Простота. Старт записи не должен занимать больше нескольких секунд.

**Пользователь.** Один человек (автор). Многопользовательность, аккаунты и публичный релиз вне границ.

**В первой версии (v1):**
- Фиксация времени вручную по глобальному хоткею (окно-палитра).
- Ручное добавление и правка записей задним числом.
- Категории (одна у записи) и теги (несколько).
- Название и необязательное описание у каждой записи.
- Журнал записей, поиск и фильтры.
- Экспорт в CSV и SQLite.

**Не в v1** (модель к ним готова, делаем отдельными циклами):
- Дашборды и аналитика (Swift Charts).
- Синхронизация между устройствами (CloudKit).
- Автоматическое отслеживание активных приложений.

## 2. Стек и окружение

| Слой | Выбор |
|---|---|
| Язык / UI | Swift 6.4, SwiftUI, строгая конкурентность |
| Хранилище | SwiftData (локально), экспорт CSV/SQLite для внешней аналитики |
| Окно-палитра | `NSPanel` (не забирает фокус у текущего приложения) |
| Хоткей | [KeyboardShortcuts](https://github.com/sindresorhus/KeyboardShortcuts) (сторонняя, проверить сканером до подключения) |
| Тесты | Swift Testing, XCTest для UI-проверок при необходимости |
| Проект | XcodeGen (`project.yml`), SwiftLint, swift-format |
| Сборка из Claude | XcodeBuildMCP |
| Окружение | Xcode 27.0 (27A266a), macOS 27 |

Backend не нужен: приложение local-first. Если появится синхронизация, сначала пробуем CloudKit.

## 3. Компоненты

Приложение обычное (иконка в Dock есть), но главный способ управления идёт через menu bar. Закрытие окна Журнала приложение не завершает.

| Блок | Задача | Зависит от |
|---|---|---|
| **Domain** | Значимые типы и чистые правила (`TimeSpan`, пересечения). Без UI и без SwiftData; SwiftData-модели `TimeEntry`, `Category`, `Tag` живут в Store | ничего |
| **Store** | Слой над SwiftData: старт, стоп, создание задним числом, правка, удаление, запросы за период | Domain |
| **PaletteParser** | Разбор строки палитры в команду (категория, теги, название, сдвиг времени) | Domain |
| **HotkeyService** | Глобальный хоткей: показать или скрыть палитру | системный API |
| **Palette** | Окно в стиле Spotlight: ввод, подсказки, Tab, Enter | Store, PaletteParser |
| **MenuBar** | Иконка с текущим таймером, popover: стоп, смена категории, поле описания | Store |
| **Journal** | Окно со списком записей по дням, панель правки, фильтры, поиск, вкладка категорий | Store |
| **Export** | CSV и SQLite по кнопке | Store |
| **Analytics** | Позже | Store |

UI не содержит бизнес-логики, а общается только со Store. Domain и PaletteParser чистые, поэтому тестируются быстро и без интерфейса. Время получается через внедряемые часы (`Clock`), а не через `Date()` напрямую.

## 4. Данные

**TimeEntry**
- `start`: начало.
- `end`: конец, пусто пока таймер идёт. Идёт ли таймер, определяется только отсутствием `end`, отдельного флага нет.
- `category`: ровно одна, обязательная.
- `tags`: 0 или больше.
- `title`: короткое название из палитры, необязательное.
- `notes`: длинное описание, необязательное (что сделал, где застрял, выводы).

**Category**: название, цвет, порядок.
**Tag**: название.

**Соглашения.**
- Время хранится в UTC, показывается в локальной зоне.
- Модель совместима с CloudKit: у полей есть значения по умолчанию, нет уникальных ограничений в базе. Уникальность названий категорий и тегов проверяет Store.

**Правила.**
1. Одновременно идёт только один таймер. Новый старт останавливает текущий в тот же момент.
2. Запись задним числом проверяется на пересечение с существующими. При пересечении показываем предупреждение, а не режем и не перезаписываем молча.
3. Удалить категорию, у которой есть записи, нельзя: сначала перенос записей в другую.
4. Время начала не может быть в будущем. Конец не раньше начала.

## 5. Хоткей и палитра

**Хоткей.** Один, настраиваемый в настройках. Нажатие открывает палитру, повторное нажатие или Esc закрывает. После Enter фокус возвращается в предыдущее приложение.

**Состояния.**
- Таймер не идёт: поле ввода и подсказки из истории (по частоте и свежести).
- Таймер идёт: сверху строка с текущей записью и временем, первой подсказкой стоит «Остановить». Пустой Enter останавливает. Ввод новой записи останавливает текущую в тот же момент и запускает новую.

**Формат ввода:** `Категория название #тег #тег [-20m]`
- Первое слово сопоставляется с категориями (нечёткий поиск), Tab дополняет.
- Остальной текст без тегов становится `title`.
- `#слово` добавляет тег, новые теги создаются сразу.
- Неизвестная категория не создаётся молча: палитра предлагает строку «Создать категорию „X“».
- Суффикс `-20m` запускает таймер как будто 20 минут назад.
- Пустой Enter при остановленном таймере предлагает повторить последнюю запись.
- Описание (`notes`) в палитру не входит, оно вносится в Журнале и popover menu bar.

**Ошибки** показываются в самой палитре, без модальных окон: пересечение (кнопки «всё равно» и «поправить»), неизвестная категория, время начала в будущем.

## 6. Журнал

- Записи сгруппированы по дням, у каждого дня сумма часов. Строка: начало, конец, длительность, цветная категория, теги, название.
- Выбор записи открывает панель справа: время, категория, теги, название, описание. Сохраняется сразу, без кнопки.
- «+ Добавить запись» создаёт запись за любой прошлый промежуток, правила пересечений те же.
- Фильтры по категории, тегу, периоду. Поиск по названию, описанию и тегам.
- Вкладка «Категории»: цвет, порядок, переименование, перенос записей перед удалением.

## 7. Экспорт

Две формы, по кнопке:
- **CSV**: одна строка на запись.
- **SQLite**: отдельный файл с таблицей `entries` тех же колонок для DuckDB/Python (не копия базы SwiftData: живую базу с журналом копировать небезопасно).

Колонки фиксированы: `start`, `end`, `duration_seconds`, `category`, `tags`, `title`, `notes`. Формат версионируется, чтобы будущая аналитика не ломалась при изменениях приложения.

## 8. Стратегия тестирования (TDD)

**Порядок.** Каждое поведение: красный тест, минимальный код до зелёного, рефакторинг. Сначала Domain и PaletteParser, затем Store, потом UI.

**Что считаем качественным тестом.**
- Проверяет **наблюдаемое поведение** (результат, состояние хранилища), а не внутреннюю реализацию.
- Падает по понятной причине, и мы видели это падение до реализации.
- Детерминирован: время идёт из тестовых `Clock`, хранилище in-memory, никакого `sleep` и зависимости от текущей даты.
- Покрывает границы: пустой ввод, ровно стыкующиеся записи (конец равен началу следующей), смена суток, летнее время, юникод и эмодзи в названиях, очень длинный текст.

**Что обязательно покрыто тестами.**
- Один таймер: старт нового останавливает прежний.
- Пересечения записей задним числом (внутри, внахлёст, вплотную, поглощение).
- Разбор палитры: категория, теги, `-20m`, неизвестная категория, пустой ввод.
- Запрет удаления категории с записями и перенос.
- Время начала в будущем, конец раньше начала.
- Экспорт: колонки, экранирование запятых, кавычек и переводов строк, пустое описание.

**Как убеждаемся, что тесты хорошие, а не просто есть.**
1. **Покрытие кода** измеряем при каждом прогоне (`-enableCodeCoverage YES`, отчёт `xcrun xccov`). Целевой минимум для Domain, PaletteParser и Store: 90% по строкам. Это нижняя планка, а не доказательство качества.
2. **Мутационное тестирование** Domain и Store (периодически, не на каждый коммит): ломаем код автоматически и смотрим, ловят ли тесты поломку. Инструмент (например, Muter) нужно проверить на совместимость со Swift 6.4 до внедрения.
3. **Правило «красный сначала»**: в плане фиксируем, что тест виден упавшим до реализации. Тест, который никогда не падал, ничего не доказывает.
4. **Ревью тестов** отдельно от ревью кода при завершении каждой задачи (`requesting-code-review`).
5. **Проверка перед завершением**: утверждаем «готово» только после реального прогона сборки и тестов (`verification-before-completion`).

**Что не покрывается автоматикой:** глобальный хоткей (нужны права системы), внешний вид и поведение окна-палитры. Проверяются вручную и по скриншотам, в плане для каждого есть чек-лист.

## 9. Окружение, безопасность, правила работы

- Перед подключением любого стороннего MCP, skill или пакета прогоняем его через cc-audit и смотрим код вручную: XcodeBuildMCP, apple-docs-mcp, SwiftUI/Concurrency skills, KeyboardShortcuts.
- `CLAUDE.md` в корне проекта: Swift 6 со строгой конкурентностью, UI без логики, команды сборки и тестов, TDD обязателен.
- Hook после правок: `swift build` и SwiftLint.
