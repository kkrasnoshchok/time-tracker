# Swift для JS-разработчика: заметки по задачам

Короткие объяснения новых концепций через аналогии с TypeScript/React. Пополняется после каждой задачи.

## Task 0: пакет и проект
- `Package.swift` = `package.json` + конфиг workspace, `swift test` = `npm test`, `@main` = точка входа приложения.
- XcodeGen: `project.yml` описывает проект текстом вместо бинарного `.xcodeproj` (его мы не коммитим, как `node_modules`).
- `@testable import X` даёт тестам доступ к `internal`-коду модуля; без него видно только `public`.

## Task 1: TimeProvider и TimeSpan
- `struct` это значение: при присваивании копируется (как неизменяемый объект с `Object.freeze`). `class` это ссылка, как обычный объект JS.
- `let` это `const`, `var` это `let`. `Date?` (Optional) это `Date | undefined`, но компилятор заставляет его обработать.
- `throws(TimeSpanError)` это типизированные ошибки: в TS `throw` принимает что угодно, здесь тип ошибки часть сигнатуры.
- `protocol TimeProvider` это TS `interface`. Мы передаём «источник времени» как зависимость, потому что вызов `Date()` внутри логики сделал бы тесты нестабильными (как `Date.now()` без `jest.useFakeTimers`).
- `Sendable` обещает компилятору, что тип можно безопасно передавать между потоками (в JS поток один, поэтому такого понятия нет).
- `Mutex` (в тестовом хелпере) защищает общее изменяемое значение от гонок между потоками.
- Тесты: `@Test` = `it(...)`, `#expect(a == b)` = `expect(a).toBe(b)`, `#expect(throws: E) { ... }` = `expect(() => ...).toThrow(E)`.

## Task 2: PaletteParser
- `enum PaletteParser` без `case` это «пустое» пространство имён со статическими функциями, как модуль с экспортами в TS; создать экземпляр нельзя.
- `enum` с ассоциированными значениями (`case existing(String)`, `case unknown(String)`) это discriminated union: в TS это `{ type: "existing", name: string } | { type: "unknown", word: string }`. `switch` обязан разобрать все варианты.
- `String` в Swift состоит из `Character` (то, что человек видит как один символ), а не из UTF-16 как в JS: `"🔥".count == 1`, а в JS `"🔥".length == 2`.
- `split(whereSeparator:)`, `map`, `prefix`, `dropFirst`, `joined` это те же `split`, `map`, `slice`, `join`, только ленивые и безопасные по границам. `\.isWhitespace` это key path: короткая запись `{ $0.isWhitespace }`.
- `guard let x = ... else { return }` это ранний выход с распаковкой Optional: в TS аналог `if (x == null) return;`, после которого `x` уже не `undefined`.
- Кортеж `(name: String, wordCount: Int)` это лёгкий безымянный объект `{ name, wordCount }` без объявления типа.

## Task 3: модели SwiftData и Store
- `@Model` это макрос: он на этапе компиляции превращает обычный `class` в сущность БД (как декоратор `@Entity` в TypeORM, только без рефлексии в рантайме). Поля с значениями по умолчанию и опциональные связи нужны для совместимости с CloudKit.
- `@MainActor` привязывает класс к главному потоку. В JS поток один, поэтому такого нет; в Swift компилятор проверяет, что вы не трогаете `TimeStore` из фонового потока.
- `class` против `struct`: модели БД это классы (ссылки: два места видят один и тот же объект), а `TimeSpan` из прошлой задачи struct (значение). `===` сравнивает ссылки, как `Object.is`.
- `#Predicate { $0.category?.id == id }` это типобезопасный фильтр запроса. Как `where` в ORM, но компилятор проверяет имена полей.
- `FetchDescriptor` + `context.fetch` это `SELECT`; `context.insert/delete/save` это INSERT/DELETE/COMMIT. Контекст ведёт себя как unit of work в ORM.
- Конфликт имён: `Category` оказался занят типом из Objective-C рантайма, который тянет `Foundation`. В JS таких «скрытых» глобальных имён нет, в Swift при импорте Apple-фреймворков они бывают, поэтому тип назван `EntryCategory`.
- `throws(StoreError)`: функция может бросить только `StoreError`. Системные ошибки (например, неудачное сохранение) мы ловим в `do/catch` и превращаем в `.saveFailed`.

## Task 4: таймер и записи
- `extension TimeStore { ... }` в другом файле дописывает методы к типу, как миксин; удобно, чтобы не раздувать один файл (в TS ближайшая аналогия — declaration merging для классов, но в Swift это обычная практика).
- `guard ... else { throw ... }` в начале функции собирает все проверки сверху («ранний выход»), а изменения данных идут только после них. Поэтому при ошибке ничего не меняется (тест `startBeforeRunningStartThrowsAndKeepsRunningTimer`).
- `var first: TimeStore? = ...; first = nil` освобождает объект: Swift сам считает ссылки (ARC), сборщика мусора нет. Мы так «закрываем» хранилище и проверяем, что таймер пережил перезапуск.
- `try?` превращает ошибку в `nil` (в JS это `try { ... } catch { return undefined }`); `try #require(x)` в тестах бросает ошибку и падает тест, если `x == nil`.
- Замыкание `{ lhs, rhs in ... }` это стрелочная функция; `sorted { ... }` принимает компаратор, как `Array.sort((a,b) => ...)`, но возвращает `Bool` («a раньше b»), а не число.
- `Set.insert(x).inserted` вставляет и сразу сообщает, был ли элемент новым: компактный способ дедупликации в порядке появления.
- Мутационная проверка вручную: мы ломали строку кода и убеждались, что тест краснеет. Если тест не краснеет, он ничего не защищает.

## Task 5: PaletteViewModel
- `@Observable` делает класс «реактивным»: SwiftUI подписывается на свойства, которые вью реально прочитала, и перерисовывает только их. Это как MobX `observable`, а не `useState`: состояние живёт в объекте, а не в компоненте.
- `didSet` на свойстве выполняется после каждой записи. Здесь он пересчитывает подсказки при вводе, как `useEffect` по зависимости `[input]`, но синхронно.
- `private(set) var items` значит «читать можно всем, менять только изнутри»; в TS это `readonly` снаружи + приватная запись.
- `for case .suggestion(let text) in items { ... }` перебирает только элементы, подходящие под паттерн enum-варианта; без `if (x.type === "suggestion")` и приведения типов.
- `defer { reload() }` выполнится при любом выходе из функции (как `finally`), поэтому каждый `return` в `submit` автоматически обновляет подсказки.
- `do { try ... } catch { ... }`: внутри `catch` переменная `error` имеет точный тип `StoreError` (благодаря типизированным ошибкам), поэтому `if case .overlap(let ids) = error` разбирается без приведений.
- View-модель не знает про SwiftUI: окно потом просто читает `items` и вызывает `submit()`. Из-за этого логику палитры можно проверить 21 тестом без единого окна.

## Task 6: группировка по дням и фильтры
- `Calendar` знает про часовые пояса и переход на летнее время. Нельзя добавлять `86_400` секунд к «началу дня»: в день перевода часов их 82 800 или 90 000. Поэтому границы берём через `calendar.date(byAdding: .day, value: 1, to:)`. В JS та же ловушка с `Date`, только без встроенного `Calendar` приходится брать date-fns/Temporal.
- `Dictionary` со значением по умолчанию: `totals[day, default: 0] += x` это `totals[day] = (totals[day] ?? 0) + x`.
- Тест, который выжил после мутации (`+86400`), показал дыру: первый DST-тест не пересекал полночь на переходе. Мутационная проверка вручную находит такие места.
- `Equatable` у структуры с `@Model`-классами работает, потому что модели Hashable по идентификатору; `==` на массивах моделей сравнивает сами записи, а не поля.
- Компилятор может отказаться проверять слишком сложное выражение («unable to type-check in reasonable time»). Лечится явным типом: `let expected: [TimeInterval] = [...]`. В TS такого нет, там вывод типов проще.

## Task 7: экспорт CSV и SQLite
- `"\r\n"` в Swift это ОДИН `Character` (кластер графем). Поэтому `ch == "\n" || ch == "\r"` не срабатывает на CRLF, и поле не бралось в кавычки: CSV ломался. Нашёл тест. Правильная проверка: `Character.isNewline`. В JS строка это UTF-16, и `"\r\n".length == 2`; здесь `"\r\n".count == 1`. Это нужно знать при любой работе со строками в Swift.
- `import SQLite3` подключает системную C-библиотеку без npm-пакетов. Указатели (`OpaquePointer`) и `sqlite3_*` вызовы это C API; `defer { sqlite3_close(db) }` гарантирует освобождение ресурса, как `finally`.
- `SQLITE_TRANSIENT` в C это макрос; в Swift его заменяет `unsafeBitCast(-1, to: sqlite3_destructor_type.self)`: говорит SQLite скопировать строку, потому что Swift может освободить свою раньше.
- Параметризованные тесты: `@Test(arguments: [...])` запускает один тест на каждое значение, как `it.each` в Jest.
- `Date.formatted(.iso8601)` даёт `2027-01-15T09:00:00Z`; форматтеры в Swift это типобезопасные «стили», а не строки формата.
- Дыры в тестах находились мутациями: если после поломки кода тесты остаются зелёными, нужен ещё тест (так добавились тесты на «чистый» перевод строки).

## Task 8: оболочка приложения и menu bar
- `@main struct TimeTrackerApp: App` с `var body: some Scene` это корень приложения; сцены (`MenuBarExtra`, `Window`) играют роль «страниц»/окон. `MenuBarExtra` рисует иконку в menu bar, а его содержимое (`.menuBarExtraStyle(.window)`) показывается как всплывающее окно.
- `@State private var model = AppModel(...)` в `App` создаёт модель один раз на всё приложение, как `useRef`/синглтон в корне React-приложения. Вью получают её параметром (`let model: AppModel`), без `Context`.
- `@Observable` + чтение свойства во `body` = автоподписка: `Text(model.menuBarTitle)` перерисуется, когда оно изменится. Каждую секунду `AppModel` обновляет `now`: это аналог `setInterval` + `setState`, только внутри `Task { while ... await Task.sleep }`.
- `@NSApplicationDelegateAdaptor` подключает старый AppKit-делегат к SwiftUI-приложению. Через него мы запрещаем завершение при закрытии последнего окна: `applicationShouldTerminateAfterLastWindowClosed` возвращает `false`.
- `TextEditor(text: $notes)` — двусторонняя привязка (`$` это `Binding`), аналог контролируемого `<textarea value onChange>`; `.onChange(of: notes)` сохраняет при каждом изменении.
- Модификаторы вью (`.padding`, `.frame`, `.font`) вызываются цепочкой и возвращают новую вью; порядок важен (как порядок обёрток в JSX).
- Приложению нужны права (Accessibility, Screen Recording) для скриншотов и управления интерфейсом; поэтому визуальные проверки мы делаем руками по чек-листу.

## Task 9: хоткей и окно-палитра
- `NSPanel` это AppKit-окно особого вида. `.nonactivatingPanel` позволяет окну принимать ввод, не делая наше приложение активным: поэтому после закрытия палитры фокус остаётся у приложения, где вы работали. SwiftUI встраивается в него через `NSHostingView(rootView:)`, как React в произвольный узел через `createRoot`.
- Глобальный хоткей даёт пакет `KeyboardShortcuts` (внутри старый Carbon `RegisterEventHotKey`, который не требует прав Accessibility). Мы фиксируем версию `exactVersion: 1.10.0` в `project.yml`, как `"1.10.0"` без `^` в `package.json`, и до подключения прочитали исходники.
- Swift 6 строго следит за общими глобальными переменными: `static let` не-`Sendable` типа запрещён («not concurrency-safe»). Лечится изоляцией на главный актор: `@MainActor static let`. В JS нет потоков, значит нет и такой проверки.
- `MainActor.assumeIsolated { ... }` говорит компилятору «этот колбэк точно вызывается на главном потоке» (хоткей приходит оттуда), без лишнего `Task`.
- `@FocusState` + `.focused($focused)` управляют фокусом поля (аналог `ref.current.focus()`); `.onKeyPress(.tab)` перехватывает клавишу и `return .handled` говорит «я обработал, дальше не передавай» (как `e.preventDefault()`).
- Двухшаговое подтверждение (Enter → вопрос → Enter) реализовано как состояние `prompt` в view-модели, а не в вью. Поэтому его можно проверить 14 тестами без окна: вью лишь показывает `prompt`.
- Зависимость `@Bindable var viewModel` даёт `$viewModel.input` — привязку к свойству `@Observable`-объекта, как `register("input")` в react-hook-form.
